# D-Link Robotics 網站規劃 v3 評審意見

評審日期：2026-11-07
評審對象：《D-Link Robotics 網站整體規劃建議 v3》（871 行，完整閱讀）
配套文件：《D-Link Robotics 數位平台系統詳細設計 v1》——本評審指出的設計缺口，在該文件中提出具體解法

---

## 1. 總評

**結論：v3 的範圍分期、責任分工與風險治理已達企業級水準，可作為「做什麼、分幾期、誰核准」的基準；但作為「怎麼做」的工程交付依據仍不足，且以目前的篇幅與語氣直接交給客戶決策者並不合適。**

| 面向 | 評分 | 說明 |
| --- | --- | --- |
| 範圍與分期 | ★★★★★ | 首發只做品牌＋免費候補，商店、會員、訂閱各有啟用條件，風險隔離正確 |
| 治理與合規 | ★★★★★ | 宣稱核准、發布台帳、決策表（D01–D14）、驗收清單（AC-01–12）都可直接用於專案管理 |
| 商業合理性 | ★★★★☆ | 不預設自建結帳、不承諾立即開通，判斷務實；但訂閱與商店的耦合風險沒有拆開（見 H3） |
| 架構可實作程度 | ★★☆☆☆ | 多為原則與責任描述，缺元件清單、介面契約、資料表、時序、部署拓撲與非功能指標數值 |
| 客戶可讀性 | ★★☆☆☆ | 7.7 萬字、大量否定句與英文術語，決策者難以在會議中使用 |
| 選項完整度 | ★★★☆☆ | CMS 只評 Sanity、商務只評 SaaS／既有商店，未提供開源或資料自主路線 |

### 1.1 v3 做得好的地方（建議保留）

1. **三種狀態分開管理**（§6.3）：內容發布、產品生命週期、市場可售性各自獨立，CTA 由三者共同決定。這是多產品網站最常出錯的地方，v3 處理得正確。
2. **首發不碰交易**（§3）：品牌網站可以獨立上線，不被金流、App、會員卡住。
3. **表單可靠性設計**（§9.2）：先持久化再回應成功、提交 ID 防重複、轉交失敗可重試，符合企業級要求。
4. **身分與權益的資料所有權拆分**（§11.2）：付款者、使用者、裝置擁有者、保固、訂閱分開建模，避免「同一 Email 自動合併帳號」這類常見漏洞。
5. **權益事件冪等與對帳**（§11.3）：已考慮亂序、重送、退款覆蓋，方向正確。
6. **GEO 不過度承諾**（§14.3）：交付「可讀取、可核實、可觀測」，不保證 AI 推薦；並正確區分搜尋爬蟲與訓練爬蟲。
7. **驗收狀態用語統一**（§15.3）：「未執行／通過／失敗／依賴未就緒／不適用」，避免把示意當完成。

### 1.2 已複核的外部事實

| v3 的陳述 | 複核結果 |
| --- | --- |
| Google 自 2026-05-07 起不再顯示 FAQ rich results | 屬實（多家來源報導；FAQ 結構化資料仍會被讀取，只是不再顯示為摺疊結果） |

## 2. 問題清單

嚴重度定義——**高**：會改變架構、預算或交付邊界；**中**：會造成體驗、維運或量測偏差；**低**：表述或可延後的完善項目。共 15 項：高 4、中 8、低 3。

### 高

**H1｜一份文件同時服務四種讀者，導致客戶無法用、工程也不夠用**
位置：文件開頭「適用：客戶提案討論、範圍確認、分期估價、設計與工程交付」。

客戶決策者需要的是 10–15 頁的選項與建議；工程需要的是介面、資料表與時序。v3 介於兩者之間：對客戶太長、太多防禦性用語（「不代表…」「不得…」「不預設…」），對工程又停在原則層。

**建議**：拆成三份——
1. **提案書**（給客戶決策者）：決策摘要、首發範圍、分期、費用結構、待決策事項。用正向語氣寫「我們會做什麼」，限制條件放附錄。
2. **規劃基準**（即現行 v3，給 PM 與雙方窗口）：保留，作為範圍與驗收依據。
3. **系統詳細設計**（給工程與客戶 IT）：本次另行提供。

**H2｜架構停在原則層，無法據以估價或開工**
位置：§8、§9、§11、§12。

缺少：元件與部署拓撲、模組邊界與程式結構、資料表、API 契約、各流程時序、事件字典與參數規格、多語實作機制、非功能指標的具體數值。例如 §7.4「CMS 發布失敗保留前一版」——若網站直接讀取 CMS 已發布內容，CMS 一旦發布，網站端事後驗證失敗也無從「保留前一版」，需要明確的閘道機制。

**建議**：以《系統詳細設計 v1》補齊；發布閘道改為「CMS 端驗證＋審核工作流為主要閘道，網站端驗證為監測與快速還原」（詳細設計 §7.5）。

**H3｜自建案件系統的範圍被低估**
位置：§9.3–9.5。

v3 在「沒有合格既有系統」時，基線是自建 PostgreSQL 收件匣＋員工操作介面（案件列表、承接、重試、刪除）＋ MFA ＋角色權限＋稽核＋雙重確認名單管理＋退信處理。這等於做一套小型 CRM／客服系統，安全責任與維護成本都很高，且會壓縮 S2 的 6–9 週。

**建議**：網站只自建「受理＋持久化＋可靠轉交」這一層；員工操作一律使用客服系統與 CRM（優先沿用 D-Link 既有工具，否則採 SaaS 或開源的 Zammad、Chatwoot、Twenty）；名單確認與退訂交給郵件行銷服務（SaaS 或開源 Listmonk）。員工身分走 D-Link 企業 SSO。詳見詳細設計 §8 與變更提案 CP-01。

**H4｜訂閱與商店沒有解耦，台灣市場風險高**
位置：§10.1、§10.4、§11.3。

v3 把 Plus 訂閱放在「商店事件＋App 收據」兩個來源。但若商店採 Shopify，其訂閱功能受付款服務限制，台灣在地金流（綠界、藍新）與 Shopify 訂閱的相容性需逐一驗證；Apple／Google 的訂閱又各有通知與驗證機制。訂閱若綁在商店平台，日後換商店就要重做權益。

**建議**：明確分工——**商店只賣實體商品（主機、配件、組合）；數位訂閱由獨立的「帳務與權益服務」負責**，彙整官網定期扣款、App Store、Google Play、客服補償四種來源，是 App 查詢權益的唯一入口。詳見詳細設計 §11 與 CP-02。

### 中

**M1｜全球預設拒絕的量測代價沒有量化**
位置：§13.1。

全站採 Basic Consent Mode、預設拒絕，品牌上一致，但多數未同意訪客將完全不在 GA4 中，候補轉換率、廣告成效只能看到部分人群。v3 已註明「只代表可觀測人群」，但沒有提出補足方法。

**建議**：(1) 營運真值改由業務資料庫計算（已確認名單、案件數），GA4 只看趨勢與行為；(2) 由法務評估分區政策：歐洲經濟區／英國嚴格事前同意，台灣與日本依當地法規決定是否採「告知＋可拒絕」；(3) 評估不使用 Cookie 的第一方彙總統計（如自架 Plausible、Umami）作為補充，前提是法務確認其處理方式。詳見詳細設計 §9.2 與 CP-03。

**M2｜缺少開源與資料自主路線**
位置：§7.4、§8.1、§10.1。

CMS 只以 Sanity 為首選，商務只評既有商店與 SaaS。D-Link 是上市公司集團，IT 與資安部門可能要求資料留在台灣、供應商審查或可自架。若 S1 才發現 Sanity 不符合集團規範，沒有備案。

**建議**：S1 做兩案實測——Sanity（SaaS）對 Payload（MIT 授權、可自架於台灣區域）；商務在 D10 決策時加入 Medusa（MIT）等開源方案作為比較組。詳見詳細設計 §7.1、§10.2 與 CP-06。

**M3｜時程的關鍵路徑是內容，而非工程**
位置：§16.2。

S2 的 6–9 週假設產品、法務與三語編輯「按約定期限審稿」。實務上宣稱核准（積分天數、雲端保存、硬體規格）與日文母語審稿通常是最慢的一環，而這些在 §7.3 都被列為發布條件。

**建議**：內容製作另立軌道與里程碑（內容凍結日、各語言交稿日），與工程軌道並行排程；週報分開追蹤。工程端以「區塊庫＋假資料」先行，避免等稿。

**M4｜企業級非功能需求全部延後到 D14**
位置：§15.4、D14。

SLO、RTO／RPO、容量、值班都等客戶核定，但客戶通常需要供應商先提出建議值才能討論。此外 v3 缺 CI／CD 流程、測試策略、基礎設施即程式碼、相依套件與供應鏈安全、WAF 與機器人防護、員工 SSO 與帳號自動停權、集中稽核日誌。

**建議**：提出可談判的預設值與完整交付工程規範。詳見詳細設計 §15 與 CP-04。

**M5｜「商務能力以獨立設定控制」需要具體機制**
位置：§6.3 末段。

**建議**：明確採用功能開關（feature flags）：商店、預購、登入、各市場開賣皆為具名開關，開關變更需核准並留下稽核紀錄，可依市場與環境分別設定。詳見詳細設計 §5.5 與 CP-09。

**M6｜LINE 管道消失**
位置：§4.3、§5.1 只剩頁尾社群圖示。

LINE 在台灣與日本是主要的品牌溝通與客服管道，v1／v2 曾列入，v3 只保留圖示。上市通知、訂單出貨通知、客服都可能需要 LINE 官方帳號。

**建議**：列為選配能力，在 D04、D07 一併決策。詳見詳細設計 §13 與 CP-05。

**M7｜日本市場的企業信任頁面延後**
位置：§6.1。

MuRu 有完整日文，但企業站只有中英。日本消費者購買陌生品牌的硬體時，習慣查看「会社概要」與隱私說明；企業日文被列為增補選項，可能影響轉換。

**建議**：首發至少提供日文的「關於／会社概要」、信任中心與隱私權政策；其他企業頁維持增補。詳見 CP-10。

**M8｜媒體管線沒有規劃**
位置：§2.3、§7.1（Asset）。

v3 只規範素材的授權與欄位，沒有圖片轉檔、響應式尺寸、影片串流與字幕的處理方式。示意站單支影片約 29MB，正式上線必須處理。

**建議**：首發納入圖片 CDN（自動 AVIF／WebP 與尺寸）、影片轉 HLS 串流、多語字幕、素材授權到期提醒。詳見詳細設計 §7.7 與 CP-11。

### 低

**L1｜程式結構「初期不預先拆套件」與後續需求衝突**
位置：§8.3。

S1 起就會有網站、背景工作（轉交、寄信）兩個執行單元，S4 還會有供 App 呼叫的權益 API，它們共用事件與資料契約。以 pnpm workspace 先分 `apps/` 與 `packages/` 成本很低，反而能用工具強制模組邊界。建議調整（CP-07）。

**L2｜根路徑 `/` 為語言選擇頁會多一次點擊**
位置：§4.2。

作為 `x-default` 正確，但台灣使用者每次從首頁進站都要多點一次。可接受；建議選擇頁同時直接顯示依瀏覽器語言建議的大按鈕，並在記住偏好後於選擇頁顯示「繼續前往上次的語言」，仍不做自動轉址。

**L3｜用語可再在地化**
storefront、adapter、owner、payload 等英文術語在客戶版應改為中文或附註；工程版可保留。

## 3. 變更提案摘要

| 編號 | 提案 | 影響的 v3 章節 | 對範圍／費用的影響 |

## 4. 建議下一步

1. 與 PM 確認是否採納 CP-01 至 CP-11，更新 v3 為 v3.1。

3. 以《系統詳細設計 v1》作為 S1 垂直驗證的工程依據，S1 結束時回寫實測結果。
